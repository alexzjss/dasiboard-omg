# Fase 1 (Base) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Google One Tap, foto de perfil própria com recorte, cargos nas entidades, badges novas (conquistas, admin, entidade, turma/curso) e tecnologias no perfil.

**Architecture:** Tudo segue o padrão atual: SQL incremental em `supabase/schema.sql`, acesso a dados só em `server/social/db.ts` (espelhado em `server/test/fakeSocialDb.ts` para os testes de rota), regras nas rotas Express, presenters como whitelist e cliente tipado em `src/lib/socialApi.ts`. O upload da foto vai direto do navegador para o Supabase Storage por URL assinada.

**Tech Stack:** React 19, Vite, Express 5 (Vercel), Supabase (Postgres + Storage), vitest + supertest + @testing-library/react, `simple-icons` (nova dependência, só ícones das tecnologias, carregada sob demanda).

**Spec:** `docs/plans/2026-10-20-cards-notificacoes-android-design.md` (seção "Fase 1").

## Global Constraints

- Textos de interface em português, no tom informal do app. Mensagens de erro da API em português, como as atuais.
- Toda escrita usa `authedWrite` (`isAllowedOrigin, requireSession, loadViewer`); leitura usa `authed`.
- Presenters nunca devolvem e-mail nem id de outros alunos.
- SQL idempotente (`if not exists`, `on conflict do nothing`), adicionado ao fim de `supabase/schema.sql`.
- Rotas nunca chamam `getClient()` diretamente: tudo passa por `server/social/db.ts`, e cada função nova ganha um equivalente em `fakeSocialDb.ts`.
- Comandos de verificação: `npm test` (vitest), `npm run lint` (oxlint) e `npm run build` (tsc + vite). Os três precisam passar no fim de cada tarefa.
- Commits em português, no estilo do histórico (ex.: "Adiciona cargos nas entidades"), terminando com `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`.

## Review Focus

1. **Path forjado na foto.** Ao confirmar a foto, alguém envia um `path` de outra pessoa (`{outroId}/x.webp`) ou com `..`. Esperado: 400. Teste na Tarefa 6.
2. **Badges vazando no perfil.** Uma badge revogada, ou de outro `kind`, aparecendo como entidade no perfil. Esperado: entidades continuam vindo só de `kind = 'entity_member'` ativos. Teste na Tarefa 2.
3. **Admin de entidade agindo fora da própria entidade.** O admin concede uma badge `entity_award` a alguém que não é membro, ou usa uma definição de outra entidade. Esperado: 404/403. Teste na Tarefa 4.
4. **Tecnologias duplicadas ou desconhecidas.** O PATCH traz ids repetidos, inexistentes ou mais de 12. Esperado: 400. Teste na Tarefa 5.
5. **Badge de turma desatualizada.** A pessoa troca `entryYear` de 2023 para 2024. Esperado: a badge "Turma 2023" é revogada e a "Turma 2024" é concedida, sem duplicar. Teste na Tarefa 3.

  - `toPerson` aplica a precedência: se `profile.avatar_path` existir, `user.picture = avatarPublicUrl(avatar_path)`; senão mantém a foto do Google. Assim todos os presenters herdam a regra sem mudanças.

    - se o objeto não existir, 404 "Envie a foto antes de confirmar";
