# Fase 3 (Card) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Carta de perfil no modelo A ("Arc fiel"), personalizável, com versão mini na Comunidade, link público `/c/:handle` com QR, coleção de cartas com animação de revelar, exportação em PNG, compartilhamento nativo e card de entidade.

**Architecture:** Um único componente `<ProfileCard>` (variantes `full` e `mini`) alimentado por um único formato de dados, `CardData`, que vem de um presenter whitelist no servidor. As opções de personalização vivem num catálogo duplicado em `src/lib/cardOptions.ts` e `server/social/cardOptions.ts`, com um teste que garante que os ids batem (mesmo padrão das tecnologias). Os desbloqueios são calculados no servidor por uma função pura e reconferidos em todo salvamento.

**Tech Stack:** React 19, CSS puro (tokens existentes), `qrcode-generator` (QR em SVG, pequeno), `html-to-image` (PNG, carregado sob demanda), Express, Supabase.

**Spec:** `docs/plans/2026-10-20-cards-notificacoes-android-design.md` (seção "Fase 3"). **Referência visual:** `.superpowers/brainstorm/3027-1792522236/content/card-arc-v2.html`, opção **A** (papel creme sobre fundo colorido, foto em forma de folha, nome grande na cor de destaque, subtítulo com cargo, etiquetas de tecnologia com separador hachurado, ícones de entidade/badge no canto, grão; verso com QR e redes). Ela não é versionada, então copiar o arquivo para `docs/plans/assets/card-arc-v2.html` na Tarefa 3.

## Adendos decididos com o Alex (valem sobre a spec)

- **Só paletas prontas, sem cor livre.** O item "cor livre + checagem de contraste" da spec sai.
  - **8 paletas Arc** liberadas para todos.
  - **3 especiais** (`neon`, `aurora`, `ouro`), desbloqueadas pelas mesmas regras dos acabamentos.
  - **Paletas de entidade**, uma por entidade, liberadas para quem é membro ativo dela. Tons pedidos pelo Alex:

## Global Constraints

- Valem as regras das Fases 1 e 2:
  - textos em português informal;
  - escrita com `authedWrite`;
  - rotas só via `server/social/db.ts`, espelhado no fake;
  - SQL idempotente ao fim de `supabase/schema.sql`;
  - `npm test && npm run lint && npm run build` verdes por tarefa, e `npx tsc -p tsconfig.server.build.json --noEmit` quando o servidor mudar;
  - commits em português com `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`.
- **Privacidade (anti-objetivo da spec):** o `CardData` nunca contém e-mail, nº USP, matérias, horários, conexões ou ids internos. As entidades e badges da carta são só as que a pessoa selecionou.
- O mesmo `<ProfileCard>` aparece em todos os lugares: perfil alheio, perfil próprio, editor, `/c/:handle`, coleção, Comunidade (mini) e exportação PNG.
- **Domínio do QR e dos links:** `import.meta.env.VITE_PUBLIC_APP_URL ?? window.location.origin` no front e `process.env.PUBLIC_APP_URL ?? frontendUrl` no servidor. Nunca escrever `dasiboard.vercel.app` no código.
- **Movimento:** tilt pelo mouse no desktop e por `DeviceOrientationEvent` no celular, com o pedido de permissão do iOS feito só por um toque explícito em "Ativar movimento". Com `prefers-reduced-motion: reduce`, nada de tilt, giro ou animação: só troca de face.
- **Bundle:** `html-to-image` só via `import()` dinâmico. O QR pode ser estático se `qrcode-generator` couber em menos de 15 KB gzip; senão, também dinâmico.

## Review Focus

1. **Vazamento na carta pública.** Uma pessoa com `card_public = false` é acessada sem login em `GET /api/cards/:handle`. Esperado: 401, sem nenhum dado da pessoa no corpo. Com `true`, o corpo não pode ter `email`. Teste na Tarefa 2.
2. **Desbloqueio forjado.** O PATCH da carta com `finish: 'gold'` ou `palette: 'ent-petsi'` sem cumprir o requisito. Esperado: 400 "Opção bloqueada". Teste na Tarefa 2.
3. **Seleção apontando para algo que a pessoa não tem.** Entidade de que ela não é membro, ou badge que não é dela, ou que foi revogada. Esperado: o PATCH recusa com 400, e na leitura o presenter descarta seleções que deixaram de valer (ex.: a pessoa saiu da entidade) em vez de quebrar. Teste na Tarefa 2.
4. **Colecionar a própria carta ou colecionar duas vezes.** Esperado: a própria dá 400; a segunda vez é idempotente (200, sem linha duplicada). Teste na Tarefa 5.
5. **Carta com dados mínimos.** Sem foto, sem cargo, sem tecnologias e sem badges. Esperado: gradiente da paleta no lugar da foto, subtítulo "curso · turma" (ou só o curso), e nenhum espaço vazio quebrado. Teste na Tarefa 3.

  - `CARD_SHAPES = ['leaf','arch','circle','squircle']`

  - `type CardSettings = { palette: CardPaletteId; paper: CardPaper; shape: CardShape; frame: boolean; grain: boolean; finish: CardFinish; entities: string[] /* entityIds, máx 4, o 1º é o "principal" do subtítulo */; badges: string[] /* `${kind}:${sourceId}`, máx 4 */; techOrder: 'profile' }`

- Desbloqueios (`cardUnlocks.ts`, função pura, só no servidor):
  - `type UnlockStats = { badgeCount: number /* não-entidade, ativas */; hasTitle: boolean; connections: number; hasAdminAward: boolean; collected: number; entityIds: string[] /* membro ativo */ }`
  - `cardUnlocks(s: UnlockStats): { finishes: CardFinish[]; palettes: CardPaletteId[]; requirements: Record<string, string> }`:
    - `common` sempre;
    - `foil` com `badgeCount >= 5`;
    - `holo` com `hasTitle || connections >= 25`;
    - `gold` com `hasAdminAward || collected >= 50`;
    - `neon` = mesma regra do `foil`, `aurora` = do `holo`, `ouro` = do `gold`;
    - `ent-X` quando `X ∈ entityIds`.
  - `requirements` traz o texto do que falta, por id bloqueado. Textos exatos:
    - foil/neon: "Ganhe 5 badges"
    - holo/aurora: "Tenha um cargo numa entidade ou 25 conexões"
    - gold/ouro: "Receba uma badge da administração ou colecione 50 cartas"
    - ent-X: "Entre na entidade {nome}"
  - db: `getUnlockStats(userId): Promise<UnlockStats>`, que reaproveita as consultas de `getAchievementStats` quando der.
- Validação: `validateCardPatch(body, ctx: { unlocks; entityIds: string[]; badgeKeys: string[] }): Validated<{ settings?: CardSettings; public?: boolean }>`, em `server/social/validation.ts`:
  - `settings` é um objeto completo e fechado (chave desconhecida dá 400);
  - todos os ids precisam estar no catálogo;
  - opções bloqueadas dão 400 "Opção bloqueada";
  - `entities` precisam estar em `entityIds` e `badges` em `badgeKeys`, senão 400 "Seleção inválida";
  - no máximo 4 de cada, e sem repetição.
- db:
  - `getCardSettings(userId): Promise<{ settings: CardSettings; isPublic: boolean }>`: faz merge de `DEFAULT_CARD` com o jsonb e descarta silenciosamente valores inválidos;
  - `updateCard(userId, patch: { settings?: CardSettings; public?: boolean }): Promise<void>`.
- Presenter: `cardData(input: { person: PersonRecord; badges: BadgeRow[]; memberships: { entityId; name; title }[]; settings: CardSettings; viewer?: { collected: boolean; connection: ConnectionState } | null }): CardData`, em `presenters.ts`:
  - `type CardData = { handle; name; picture: string | null; subtitle: string; course: string; entryYear: number | null; technologies: string[]; links: Links; entities: { entityId; name; title: string | null }[]; badges: Badge[]; settings: CardSettings; viewer: { collected: boolean; connection: ConnectionState } | null }`
  - `subtitle`: com a 1ª entidade selecionada tendo cargo, `"{title} · {name}"`; senão `"{course} · Turma {entryYear}"`, ou só `course` sem ano.
  - Descarta as seleções que não valem mais.
- Rotas (`server/routes/cards.ts`):
  - `GET /api/me/card` (`authed`) → `{ settings, public: boolean, unlocks, card: CardData }`
  - `PATCH /api/me/card` (`authedWrite`) → mesmo formato. Recalcula os desbloqueios no servidor.
  - `GET /api/cards/:handle` (`optionalSession` + `rateLimit('card-read', 120, 10 * 60_000)`):
    - logado: `CardData` com `viewer`;
    - anônimo com `card_public`: `CardData` com `viewer: null`;
    - anônimo sem `card_public`: 401 `{ error: 'Entre para ver esta carta' }`;
    - handle inválido ou inexistente: 404.
  - `optionalSession`: lê o cookie como `requireSession`, mas segue sem `req.user` quando não houver sessão. Depois dela, um `loadViewerIfAny` que chama a lógica de `loadViewer` só quando há `req.user`.
- Cliente: `getMyCard()`, `updateMyCard(patch)`, `getCard(handle)`, mais os tipos `CardData`, `CardSettings` e `CardUnlocks` em `socialApi.ts`.
